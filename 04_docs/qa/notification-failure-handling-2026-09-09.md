# 알림 실패 처리 개선 — 2026-09-09

## 상태와 범위

앞선 [알림 검수](./notification-audit-2026-09-09.md)에서 발견한 세 가지 실패 처리 문제의 후속 수정이다. 이번 변경은 **로컬 수정·검증**이며 커밋·푸시·운영 배포·실제 알림 전송은 하지 않았다. 운영 서버의 직전 숙제 redirect 수정 배포와 구분한다.

ntfy 원문/줄바꿈, 설정의 ntfy 코드와 앱 알림함 연결은 그대로 둔다. PWA 코드·버전·데이터베이스·시크릿·의존성을 변경하지 않았다.

## 바뀐 실패 처리

- 자동화 ntfy 발송이 실패하면 예외를 전달하여 작업을 실패 종료한다. 실패 알림까지 실패하더라도 원래 작업의 실패 종료 코드는 유지한다. 고정 ntfy CLI도 실패 시 종료 코드 1이다.
- Solapi HTTP 성공과 실제 접수 상태를 함께 확인한다. 접수 거절·미설정은 `failed`, 응답 유실/깨진 응답/서버 오류는 `unknown`으로 구분한다. 성공은 접수 확인이지 휴대폰 도착 보증이 아니다.
- OTP·별도 숙제 알림 API는 접수 실패에 `ok:false, sent:false`와 502/503을 응답한다. 실제 상담·숙제 저장은 성공한 상태로 유지하며 알림 실패만 분리한다.
- 릴레이/상담 카카오/숙제 카카오의 운영 경고는 `ctx.waitUntil`로 처리한다. 경고 지연·실패 때문에 이미 완료된 저장을 실패로 응답하지 않는다.
- 직접 Worker ntfy 경고의 중복 방지 기록은 접수 성공 뒤에만 저장한다. 첫 실패 때문에 다음 경고까지 차단되는 문제를 제거했다.
- Worker 정시 실행은 각 발송 창 시작 이후의 성공만 인정한다. 새벽 수동 실행 성공이 그날 저녁의 다른 대상 발송까지 막지 않는다.

## 학생·상담 D-1의 수신자별 재시도

`notification_batch.mjs`와 `notification_ledger.mjs`는 기존 GitHub Actions 실행 로그·기본 토큰으로 수신자별 체크포인트를 복원한다. 전화번호·이름·본문을 기록하지 않고 기존 Solapi 시크릿으로 만든 비식별 키와 서명을 기록한다.

| 이전 상태 | 다음 실행 |
|---|---|
| accepted | 이미 접수했으므로 전송하지 않음 |
| failed | 해당 수신자만 재시도 |
| pending / unknown | 자동 전송하지 않고 결과 불명으로 보고 |
| 기록이 없음 | 시도 기록을 먼저 남긴 뒤 전송 |
| 기록 조회·검증 실패 | 전체 발송 중단, 실패 종료 |

- 같은 명단의 중복 키는 한 번만 처리한다. 일부 실패가 있어도 다른 미발송 수신자를 처리한 뒤 접수/기존 접수/실패/결과 불명 수를 보고한다.
- 두 workflow를 각각 직렬화해 정시·백업·수동 실행이 동시에 발송하지 않도록 했다.
- 서명에 workflow·업무 날짜·run ID·attempt·연속 순번을 넣어 공개 로그의 서명 줄을 다른 실행에 재생하거나 학생 입력으로 위조하지 못하게 한다.
- 같은 run의 이전 attempt도 복원한다. 자정을 넘긴 동일 배치의 수동 재실행은 전날과 당일 로그를 조회하고, 자동 D-1 발송은 17~21시 창 밖에서 전송하지 않는다.
- 실행 전 취소 또는 해당 발송 단계의 명확한 생략만 복원 대상에서 제외한다. 실제 실행된 job의 기록이 없거나 서명이 잘못되면 미발송으로 가정하지 않는다.
- GitHub 로그 다운로드는 인증된 API의 302 응답 주소만 사용하고 다운로드 요청에는 인증 헤더를 전달하지 않는다. 페이지·로그 크기·요청 시간에 상한을 둔다.

## 검증

- Worker 전체 테스트: **29개 파일, 532개 통과** (`npm test`). 실제 workerd의 숙제 제출·redirect 회귀 검사, 실패 응답·경고 비동기 처리·중복 방지·예약 시간 경계를 포함한다.
- 별도 Node 자동화 테스트: **19개 통과** (`ntfy_privacy.test.mjs`, `secure_ntfy_topics.test.mjs`). ntfy 원문과 줄바꿈 보존·토큰 비노출도 확인했다.
- 위 532개에는 로그 복원 75개, 실제 D-1 스크립트의 새 프로세스 재실행 19개가 포함된다. 접수/결과 불명 상태의 자정 이후 복원, 새벽 자동 실행 차단과 저녁 새 배치 구분을 검증했다.
- Worker 배포 전 번들 검사: `wrangler deploy --dry-run` 통과, 336.51 KiB / gzip 73.84 KiB. 실제 업로드·배포는 하지 않았다.
- 학생·상담 workflow YAML 파싱과 각 concurrency 그룹·읽기 권한 설정 검사를 통과했다. 기존 설치된 파서를 사용했으며 의존성 추가는 없다.

검증에는 실제 두 D-1 스크립트를 별도 Node 프로세스로 실행하는 테스트가 포함된다. 첫 프로세스의 서명 로그를 다음 프로세스의 합성 GitHub 로그 응답으로 복원하여, 일부 실패 재시도와 결과 불명 보류가 프로세스 재시작 뒤에도 유지되는지 확인한다.

모든 Notion·Solapi·GitHub·ntfy 요청은 합성 응답으로 대체했다. 실제 학생/강사 알림·숙제·운영 데이터를 생성하지 않았다.

## 운영 적용 시 주의

- 이번 변경은 **아직 운영 미반영**이다. 적용하려면 자동화 코드/workflow를 main에 반영하고 Worker를 배포해야 한다. PWA 배포는 필요 없다.
- GitHub 로그는 영구 데이터베이스가 아니다. 로그 누락·만료·서명 키 변경은 안전 보류하며, 로그 끝부분 자체의 유실까지 포함한 중복 0을 보증하지 않는다.
- 적용 당일에 구버전으로 실행된 job은 서명된 시작 표식이 없다. 발송 상태를 추정하여 재실행하지 않고 `unrecognized_log`로 보류한다. 전환은 기존 배치가 끝난 뒤 다음 발송 업무일 전에 하는 편이 안전하다.
- `unknown`은 실패 확정이 아니다. Solapi 내역/수신 여부를 확인하기 전 수동 재발송도 하지 않는다. 일반 workflow 수동 재실행은 이 보류를 우회하지 않는다.
- 조회 범위는 배치 업무 날짜와 필요시 다음 날까지이며, 서로 다른 과거 날짜의 임의 run을 뒤늦게 실행하는 모든 운영 방식까지 전역 멱등성을 보장하지 않는다.
- ntfy 릴레이의 GitHub 접수는 ntfy 실제 발행이나 휴대폰 수신과 다르다. 이번 작업이 새로운 영구 발송 큐나 모든 실패의 자동 재전송 보장을 추가한 것은 아니다.
- 현재 PWA의 숙제 알림 호출은 비동기 부가 요청이며 새 API 오류 응답을 토스트로 표시하지 않는다. 해당 실패는 운영 경고로 알린다. OTP는 기존 실패 화면을 사용한다.
